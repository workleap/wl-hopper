# Publishing Hopper as an agent Skill

## Status

Proposed

Related: [Hopper MCP Server](https://hopper.workleap.design/getting-started/ai-for-agents/mcp-server) — the surface this builds on
Reference implementation: [React Aria](https://react-aria.adobe.com) (`npx skills add https://react-aria.adobe.com`)

## Context

Hopper already exposes three surfaces to AI agents:

- **`llms.txt` / `llms-full.txt`** — paste-into-a-chat documentation, served from the docs site.
- **The MCP server** — `https://hopper.workleap.design/mcp`, a Netlify function exposing 6 tools, 2 prompts, and 8 resources over the generated AI docs.
- **The AI docs pipeline** — `apps/docs/ai-pipeline/`, a declarative config that renders `apps/docs/content/**` MDX into ~20 MB of markdown and JSON under `apps/docs/dist/ai-docs`. Both surfaces above read from it.

The MCP server works well but has an adoption ceiling. It requires per-agent configuration (a `.vscode/mcp.json`, a `.mcp.json`, a Cursor settings entry), a live HTTP endpoint, and an agent that supports MCP at all. Teams that would benefit most — someone opening a Workleap repo for the first time and asking an agent to add a form — are exactly the teams least likely to have configured it.

**Agent Skills** are the lower-friction channel. A skill is a folder of markdown with a `SKILL.md` entry point; agents load the description eagerly and the reference files on demand. Installation is one command, the content works offline afterwards, and the format is agent-agnostic.

What other design systems and tools do:

- **React Aria** — publishes a skill from its own docs site via a `/.well-known/skills/index.json` endpoint. 167 files, 3.2 MB, one markdown file per component, plus guides, interactions, and utilities. `SKILL.md` is 16 KB: a hand-written "hot path" section, then a generated index of the `references/` tree.
- **Figma** — serves skills through its MCP server's resources (`skill://figma/...`), coupling the skill to the MCP rather than replacing it.
- **Most design systems** — `llms.txt` only, which Hopper already has.

The relevant observation for Hopper: **almost everything the MCP does is document retrieval over artifacts the pipeline already generates.** `get_component_doc` reads a generated markdown file. `get_guide` reads a generated markdown file. Those are files, and in a skill, files are the interface.

Three tools do real computation rather than retrieval — `validate_hopper_code` (a JSX AST linter), `get_design_tokens` (filtering and format conversion over the token maps) and `get_icons` (Fuse.js fuzzy search). Those are the ones that need code, not just data, on the skill side.

One protocol constraint shapes the design: the `skills` CLI errors and demands an explicit `@selector` when a host advertises more than one skill. Publishing a family of skills would break the bare `npx skills add https://hopper.workleap.design` command that makes this worth doing.

One pre-existing bug blocks it: the docs site's `rewrites()` rule `/:path*.:ext(txt|md)` already swallows every `.md` path under `/.well-known`, so `https://hopper.workleap.design/.well-known/skills/hopper/SKILL.md` returns `400` today.

## Decision

Publish **one skill, named `hopper`**, generated by a new build stage that composes the existing `dist/ai-docs` output, and served from the docs site at `/.well-known/skills/`. Keep the MCP server; it remains the authoritative, always-current surface.

| Decision              | Choice                                                                                                                                                                                        |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Number of skills      | One (`hopper`). The Figma-to-code workflow is a section inside it.                                                                                                                            |
| Generation            | A separate compose-only stage (`scripts/buildSkills.ts` + `ai-pipeline/skills.config.ts`) over `dist/ai-docs` — not a new build type in `ai-docs.config.tsx`.                                 |
| Scope                 | The MCP's **6 tools** and **2 prompts**, minus Orbiter migration. The 8 `hopper://` resources are **not** ported.                                                                             |
| Component docs        | Split — `usage` markdown + `brief` props JSON — rather than the merged `components/full` markdown.                                                                                            |
| Payload               | ~4.8 MB, ~326 files. `components/api/full`, `llms-full.md`, `*/index.md` merge artifacts and `changelogs.md` are excluded.                                                                    |
| Computation           | Bundle the MCP's own `validatorService`, `tokensService` and `iconsService` into `scripts/*.mjs`. No logic is reimplemented; only data paths and the JSX parser are swapped.                  |
| Serving               | Netlify `[[redirects]]` with `force = true` onto static `public/agent-skills/**`, plus a matching Next `beforeFiles` rewrite for local dev. Not a route handler, not `public/.well-known/**`. |
| Distribution          | A single `hopper.tar.gz` advertised through the 0.2.0 discovery schema with a sha256 digest, not a per-file list.                                                                             |
| Versioning            | Snapshot at install time; regenerated on every docs deploy. Re-running `npx skills add` is how you update.                                                                                    |
| Checked into the repo | No. It is a gitignored build artifact, like `apps/docs/public/ai-docs`.                                                                                                                       |

### Why Orbiter migration is not ported

The MCP exposes `migrate_from_orbiter_to_hopper`, and the pipeline generates an Orbiter→Hopper
component mapping table. Neither goes into the skill: Orbiter is officially deprecated and its
migration deadline has passed, so shipping migration guidance in a _new_ surface would point agents
at work that is no longer happening. The MCP tool stays for the codebases still finishing that
migration; removing it is a separate decision.

The skill's `description` is also free of Orbiter trigger terms, so it does not claim a capability
it no longer carries.

### Why resources are not ported

`apps/mcp-server/src/resources.ts` registers `hopper://llms-full`, `hopper://components/{name}/usage`, `.../props`, `.../props-full`, `hopper://tokens/{category}`, `hopper://token-guides/{category}`, `hopper://guides/{section}`, `hopper://icons/{type}`, and `hopper://component-list`.

Every one of them addresses a file the tools already serve. MCP has resources because the protocol distinguishes model-invoked tools from client-attached context; a skill has no such split — `references/components/Button.md` _is_ the resource. Porting them would ship the same bytes twice under two paths for no behavioural gain.

Prompts are different and _are_ ported. Skills have no prompt primitive, so `build_hopper_app` and `generate_code_from_figma_design` become workflow documents under `references/workflows/`. They are authored guidance, not a duplicate addressing layer, and the Figma checklist in particular is the densest Hopper-specific guidance we have written anywhere.

## Consequences

### Positive

- Zero-config adoption: one command, no MCP client, no server round-trip. Works in any Skills-compatible agent.
- Works offline and inside sandboxed CI, where the MCP endpoint may be unreachable.
- `apps/docs/content/**` stays the single source of truth and now feeds three surfaces (docs site, MCP server, skill) from one pipeline.
- The validator stays a single implementation — the skill bundles the MCP server's source rather than forking it.
- Fixes the pre-existing `400` on every `/.well-known/*.md` request as a side effect.
- Progressive disclosure means an agent pays for `SKILL.md` (~16 KB) up front and only reads the component files it actually needs.

### Negative

- A **third** consumer of the ai-docs output. Renaming a route in `ai-docs.config.tsx` now breaks three things instead of two. Mitigated by hard build failures in `buildSkills.ts`, a static consistency test that runs in PR CI, and a `pnpm build:skills` CI step that builds the skill for real on every PR.
- The skill is a snapshot. It goes stale until the consumer re-installs, whereas the MCP is always current. Acceptable for component docs and tokens, which change on a release cadence, not hourly.
- `props-full` stays MCP-only; the skill ships brief props and links the full JSON online.
- Carrying the token and icon services meant shipping the whole token map tree (1.95 MB, up from the 0.65 MB `all.json` roll-ups) so per-category lookups resolve the way they do on the server. That is most of the growth from ~3.3 MB to ~4.8 MB. The alternative — skill-only category filtering over `all.json` — was rejected precisely because it would be logic the MCP does not have.
- Converting `rewrites()` from the array form to the `{beforeFiles, afterFiles}` object form touches a route surface that has no automated coverage today. Requires manual regression checks on the deploy preview.
- The same rewrite has to be declared twice, in `next.config.js` for `next dev` and in `netlify.toml` for production (see option G). They can drift.
- The bundled validator depends on a parser resolvable from the consumer's project. Full fidelity requires `typescript` or `@typescript-eslint/parser` to be installed; the bundled `acorn-jsx` fallback handles plain JSX but not TypeScript-only syntax.

### Neutral

- `/.well-known/skills/` is a de-facto convention established by the `skills` CLI, not a ratified standard. The manifest shape may change; the generation stage is small and config-driven, so following it is cheap.
- Skill content competes with the consumer's context budget in a way MCP tool calls do not — the agent decides what to read, and a badly-sized reference file is a real cost. This is why the payload is curated to ~3 MB rather than shipping all 20 MB.
- The docs site now publishes a build artifact under two paths (`/ai-docs/**` for the MCP and humans, `/.well-known/skills/**` for skill clients) with partly overlapping content.

### Why the skill ships as an archive

The `skills` CLI has two download paths. The per-file one (`fetchLegacySkillByEntry`) fires one
`fetch` per advertised file with no concurrency limit and swallows every failure — `catch {}`
returns `null` and the file is silently skipped. At this skill's size that reliably loses files:
measured 263-317 of 326 across runs, with `scripts/` missing every single time, because it sorts
last and holds the largest files. Nothing in the CLI's output indicates a partial install.

So `index.json` uses the 0.2.0 discovery schema and advertises a single `hopper.tar.gz` with a
sha256 digest. The client makes one request and verifies the digest, so an install is either
complete or a visible failure. It also transfers ~10x less (0.52 MB compressed against 4.8 MB).
Measured 326/326 with all three scripts present on every run.

The loose files stay published alongside it — they cost nothing extra and are convenient to `curl`.

The tradeoff: a client that only understands the 0.1.0 per-file schema will not read a 0.2.0 index.
Given the per-file path is the one that is broken at this size, that is the right way round.

## Options considered

### Option A — A family of skills (`hopper`, `hopper-figma-to-code`, …)

Split by trigger surface so each skill's description competes for a narrower set of prompts.

- Considered because a workflow like Figma-to-code has genuinely distinct triggers and a distinct audience.
- Rejected because the `skills` CLI requires an `@selector` when a host advertises multiple skills, which breaks the bare `npx skills add https://hopper.workleap.design` command. Worse, no satellite skill is useful without the component catalog and token maps, so ~1.5 MB of references would have to be duplicated into each — skills are fetched into separate directories and cannot share files.

### Option B — A new build type inside `ai-docs.config.tsx`

Add `skills/*` routes to the existing config rather than a second stage.

- Considered because one config is simpler to explain than two.
- Rejected on two counts. `aiDocsConfig` has a single output root that `buildAiDocs.ts` wipes, so skill output cannot live elsewhere without changing a type shared by build and serve. And the serve-side reverse lookup (`findMatchedAiFiles`) iterates every route to derive candidate paths, so skill routes would add bogus candidates and make `/txt` resolution non-deterministic for ordinary `/components/*.md` requests.
- A third argument applied when this was written and no longer does: `generateFilesMapping` would have doubled the `files` object exported to `@docs/ai`, forcing hand-edits to a 2,681-line manual mock in `apps/mcp-server/src/tests/mocks/aiFiles.ts` for files the MCP never reads. That mock was deleted in #1003, which now syncs real AI docs into `apps/mcp-server/src/.docs` instead. The two remaining reasons stand on their own.

### Option C — Prose instructions instead of bundled services

Document the validator's rules in prose, and tell the agent to `grep` the token and icon JSON.

- Considered because it needs no bundling and no runtime dependency. This is how the skill started.
- Rejected as the _primary_ mechanism on all three counts. Prose validation gives no deterministic pass/fail, and "does this prop value exist in the token map" is exactly the kind of question agents get wrong confidently. `grep` over `icons/data.json` is materially worse than the Fuse.js search — exact substring matching misses the synonym hits that make the keyword field worth having. And token lookup by hand invites the token-name-versus-prop-value mistake the whole page warns about.
- Instead, each of the three is a bundled script over the MCP's own service, so the two surfaces cannot answer differently. The markdown rules are kept as the validator's documented fallback for when no JSX parser resolves.

### Option D — Bundle `@typescript-eslint/parser` into the validator script

Ship a fully self-contained validator.

- Rejected: the parser transitively pulls in `typescript`, roughly 8 MB — nearly three times the entire skill budget, for one script.
- The chosen middle path resolves the parser at runtime from the consumer's `node_modules` (every Hopper consumer is a TypeScript React app) and falls back to a bundled `acorn` + `acorn-jsx`, whose ESTree-compatible JSX nodes are what the validator's helpers already walk.

### Option E — Publish the skill as an npm package

`npm i -D @hopper-ui/skill` and let a postinstall place the files.

- Considered because the repo already has changesets and npm trusted publishing wired up.
- Rejected because it inverts the ergonomics the skill exists to provide: it requires a dependency, a lockfile change, and a review, where `.well-known` requires one command and no repo change. It also fragments versioning — the skill would drift from the deployed docs it describes.

### Option F — Ship merged `components/full/*.md`, one file per component

Mirror React Aria's layout exactly: usage and props in a single file per component.

- Considered because one read per component is simpler for the agent to reason about, and it is the shape the reference implementation uses.
- Rejected because Hopper's merged files are large — `Button.md` is 52 KB (~15k tokens) against a ~6.5 KB median for the usage-only variant. The split also mirrors the `doc_type` distinction the team already validated in `get_component_doc`, and saves ~590 KB. `SKILL.md` compensates by stating the read order explicitly: the component file first, the API JSON only when an exact type or default is needed.

### Option G — Serve from `public/.well-known/**` directly, or from a route handler

- `public/.well-known/**`: Next's public-directory collection and `@netlify/plugin-nextjs`'s static-asset globbing both treat dot-prefixed _directories_ inconsistently, and the behaviour cannot be verified without a deploy. Rejected as the primary mechanism.
- A route handler (`app/well-known-skills/[...path]/route.ts`) works — `app/txt/[...path]/route.ts` proves the pattern on Netlify — but adds a path-traversal surface, manual MIME mapping, and pushes every byte of a 3 MB skill through a Lambda instead of the CDN. Kept as the fallback if the redirect rules ever stop working.
- A Next `beforeFiles` rewrite alone was the first attempt. **It does not work on Netlify.** Measured on the deploy preview: `public/agent-skills/**` is published and served correctly (`/agent-skills/hopper/SKILL.md` → 200 `text/markdown`), but `/.well-known/skills/hopper/SKILL.md` reaches the Next server, where the `afterFiles` `/:path*.:ext(txt|md)` rule claims it and the `/txt` handler answers `400`. `@netlify/plugin-nextjs` does not honour `beforeFiles` for these paths.
- The chosen answer is Netlify `[[redirects]]` with `status = 200` and `force = true` onto `public/agent-skills/**`. User redirects in `netlify.toml` outrank framework-generated ones, and `force` is required so the rule beats the Next catch-all. This keeps CDN delivery and correct content types with no new server code. The `beforeFiles` rewrite stays in `next.config.js` because it is what makes `npx skills add http://localhost:3000` work against `next dev`. CORS headers are declared in both places for the same reason — Next's `headers()` does not apply to a CDN-resolved rewrite.
